Arena Companion

A mobile field assistant for volunteers working in and around event arenas. The product is designed to make the next action obvious, reduce uncertainty, and keep operational information useful even in weak network conditions.

Primary goal
Reduce uncertainty during live volunteer work
Main users
Volunteers and shift leaders
Platform
Android mobile application
Core lens

Why the flow works

Three interaction principles

Short path to action

The app should help the user act with one or two taps, not browse through menus.

Clear confirmation

Check-in and reporting screens must always communicate whether the action succeeded.

Strong feedback

Weak connectivity is expected, so the interface must explain local save and sync status clearly.

Field-friendly structure

The user should always know the next task, current place, and reporting path.

MVP feature set

What the first usable version must include

Shift overview

Time, role, assigned area, and immediate instructions.

OpenStreetMap view

Venue orientation with checkpoints, incidents, and current context.

QR check-in

Fast presence confirmation at checkpoints or task locations.

Incident report

Structured issue capture with location, category, and optional photo.

System feedback

What the interface should always communicate

Action started

The user can tell that the selected task or report flow has opened correctly.

Confirmation ready

Check-in states should clearly indicate when the app is ready for final confirmation.

Saved offline

Weak signal should never make the user wonder whether the report was lost.

Synced later

Background upload should resolve queued items without creating extra admin work.

System structure

How the mobile UI connects to the wider system

Mobile client

Compose UI, task flows, map view, QR scan, incident form, local cache, and session state.

↔

Backend services

Authentication, volunteer identity, shifts, tasks, reports, messages, and media storage.

Offline layer

Stores a working subset of data and pending actions for unstable network conditions.

→

Background sync

Uploads queued actions later and keeps the user informed about local save vs synced state.

Authentication

Login and session handling

Proposed flow

  • Volunteer signs in through backend authentication.
  • The app stores a session token locally instead of a raw password.
  • Shift data and recent tasks are cached after login for faster reuse.
  • Session state remains visible even when the network becomes unstable.
Constraints

Technical realities already considered

Design implications

  • No Google Maps dependency: OpenStreetMap-based rendering is preferred.
  • Battery and permission usage must stay reasonable during long shifts.
  • Offline-first handling matters because crowd-heavy venues weaken connectivity.
  • Camera, QR, and location features should support the task instead of slowing it down.

Scope decisions

What belongs in the first milestone

Core MVP boundary

  • Show the current shift, role, and next action immediately.
  • Provide map-based orientation with OpenStreetMap support.
  • Allow QR check-in and a short structured reporting flow.
  • Preserve critical actions locally when the network is weak.
Open design questions

What still needs product decisions

  • How much map detail is helpful before it becomes distracting?
  • Which incidents need the shortest reporting flow?
  • Should shift leaders use the same client or a lighter variant?
  • How much offline support is enough for the first usable prototype?
