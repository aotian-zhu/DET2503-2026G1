# Arena Companion — P1

An Android application for volunteers at the 2029 FIS Alpine World Ski Championships in Narvik. P1 extends A2 with an Arctic blue Material 3 interface, OpenStreetMap, foreground GPS, proximity features and persistent offline data.

**Version:** 0.5.2 (version code 7). **Application ID:** no.dte2503.volunteer.p1.

## Submission contents

The submission ZIP contains exactly these three items at its top level:

- **P1/** — the Android Studio project, including source, resources, Gradle wrapper and automated tests.
- **ArenaCompanion-P1-10min-demo.mp4** — the team's final Samsung phone demonstration, approximately ten minutes (10 minutes 28 seconds), with audio.
- **README.md** — setup, functionality, documented test scenarios, known issues and limitations.

The ZIP excludes compiled APKs, build output, local credentials, IDE settings, caches, screenshots, development logs and recording guides. In the Git repository, this README is in P1 and the video/ZIP are in P1/deliverables.

## Setup and running

1. Extract the whole ZIP. In Android Studio, choose **Open** and select the extracted **P1** folder containing settings.gradle.kts.
2. Install **Android SDK 35** and **Build Tools 35.0.0** if prompted. Internet access is required for the initial SDK/dependency download.
3. In Android Studio's Gradle settings, select **JDK 17 or 21**, then sync. The wrapper is **Gradle 8.11.1** with **Android Gradle Plugin 8.9.1**; avoid JDK 25 with this wrapper. Validation on the development computer used JDK 23.
4. Select an emulator or Android phone running **Android 8.0 / API 26 or newer**. For a phone, enable USB debugging and accept its debugging authorization.
5. Select the **app** run configuration and press **Run**. Android Studio creates local.properties with the local SDK location.
6. On the welcome screen, tap **Explore the volunteer demo**. No account, password or API key is needed for the demo. If a saved session opens directly, continue using it or choose **You → Leave demo** to return to the welcome screen.

If an emulator displays a black screen, change its graphics mode to **Software** in Device Manager and use **Cold Boot**. Android API 35 is suitable for this application.

The source is under **P1/app/src/main/java/no/dte2503/volunteer** in the extracted ZIP. Screen code is in ui/screens, data/repository code in data, and location/connectivity code in platform. Unit and device tests are under app/src/test and app/src/androidTest.

From a Windows terminal inside the project folder:

~~~powershell
.\gradlew.bat :app:assembleDebug
.\gradlew.bat :app:testDebugUnitTest :app:lintDebug
# With an emulator or phone connected:
.\gradlew.bat :app:connectedDebugAndroidTest
~~~

On macOS/Linux, make gradlew executable with chmod +x gradlew and use ./gradlew for the equivalent tasks. The generated debug APK is app/build/outputs/apk/debug/app-debug.apk; it is intentionally excluded from the submitted source archive.

## Optional existing team accounts

The Android client preserves the group's A2 Supabase integration. The source ZIP does not contain machine-specific local.properties, volunteer passwords or privileged keys. Without optional backend configuration, use the self-contained demo.

To enable existing team sign-in, add the existing course/team backend's public client settings to the local.properties generated by Android Studio, then rebuild:

~~~properties
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_CLIENT_KEY
~~~

Use the provided team's existing configuration and volunteer email/password. Keep the generated sdk.dir setting. Do not use a service-role/admin key in an Android application. A commented local.properties.example is included in the project. This submission does not create or modify a backend, database schema or user accounts; those services must already be available.

If the demo is open, choose **You → Leave demo** before signing in. First load the real account online so its data can be cached.

## Main workflows

- **Today:** shift summary, completed-task progress, current Narvik weather, next task, closest unfinished task and meeting-point distance.
- **Tasks:** All/Open/Done filters, task progression, **Reopen task** for accidental completion, map links and coordinator conversations.
- **Map:** OpenStreetMap, interactive task/facility markers, current position and accuracy, distance ordering, walking estimates and arrival reminders.
- **Inbox:** announcements, persistent read state, coordinator conversations, saved message drafts and **My task updates** history.
- **You:** volunteer information, saved System/Light/Dark appearance, offline/sync indicators and **Check this device** with editable expected/observed results and report export.
- **On-site essentials:** demo QR/checkpoint confirmation with duplicate protection, incident reporting, persistent drafts and optional photo selection.

Demo volunteers, shifts and operational assignments are fictional; coordinates are approximate. Weather is real current Narvik weather from Open-Meteo, not a forecast for the 2029 event.

## Location, permissions and offline behavior

On Map, choose **Locate me** and allow location **While using the app**. Precise location improves distance and arrival accuracy. Denying permission leaves the saved locations available and provides recovery guidance. The app does not collect a background location history or upload the volunteer's GPS position.

For an emulator test in central Narvik, set **latitude 68.4384, longitude 17.4272** in Extended Controls → Location. Foreground location continues while navigating between app screens and stops when the activity is no longer visible. Old or stale fixes are rejected/cleared.

Choose **Map → Facilities → Volunteer hub → Watch arrival** to watch a 150 m zone. An accurate fix must confirm entry; a wider exit boundary prevents repeated alerts from GPS jitter. **Demo walk** deliberately uses labelled practice positions and pauses the displayed phone GPS. Choose **Use GPS** to return to the real position.

Task status, cached operational information, message/incident drafts, announcement reads, appearance and test observations are saved locally using Android AtomicFile. They remain available after an offline restart. Previously browsed map tiles may be cached; unvisited map imagery needs internet. Current weather shows its source/time and retains a saved reading when refresh fails.

For configured accounts, task-status and announcement-read changes use a persistent outbox and retry when the app reconnects, resumes or refreshes. The latest offline task state is retained. Demo changes stay on the device and are labelled accordingly.

Camera permission is requested for QR scanning. Incident photos use Android's document picker, without broad storage permission. The built-in **Try the demo checkpoint** workflow can be demonstrated without a printed QR code.

## Known issues and limitations

- No blocking defect was observed in the documented emulator scenarios. The application has not been validated on every phone, Android version, screen size or accessibility configuration.
- API 37 preview emulation experienced host memory pressure; software graphics, a cold boot and running builds separately from emulation were used during validation.
- Offline map imagery is limited to previously cached tiles. Markers and saved data remain useful without guaranteeing imagery everywhere.
- GPS can be inaccurate, unavailable or delayed indoors. There is no indoor positioning.
- Walking times assume 4 km/h over straight-line distance, with a 20 km limit and accuracy checks. They do not account for actual walking routes, terrain, snow or restricted access.
- GPS tracking and arrival reminders run only while the app is visible. There are no background geofence notifications or push notifications.
- Backend synchronization runs in the foreground. Task/read updates coalesce, but general multi-user conflict resolution is outside this milestone.
- Remote messages, incident submissions and QR confirmations require internet. They are not automatically replayed, because the existing service operations could otherwise create duplicates.
- There is no registration/account-management flow or coordinator dashboard. Existing volunteer accounts must be provisioned externally; Inbox data refreshes rather than using a live push feed.
- Photo access can be revoked by Android. Reselect an inaccessible photo. JPEG, PNG and WebP files up to 5 MB are accepted; there is no photo resizing.
- The interface is English. Demo data is a course scenario, not the organizer's actual 2029 operational plan.
- Uninstalling or clearing application data removes local drafts, demo progress and caches.
